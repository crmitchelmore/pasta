# Application dependency resolution

The macOS SwiftPM entrypoint and the iOS Xcode workspace commit separate
`Package.resolved` files with identical source revisions. CI and macOS release
commands use `--force-resolved-versions`; iOS resolution, build settings,
simulator builds and archives use `-onlyUsePackageVersionsFromResolvedFile`.
Missing or outdated pins must fail native resolution instead of choosing a
new dependency for an already-tested source commit. The portable verifier
rejects missing, invalid or different pins across the two entrypoints.

The initial schema-v2 lockfiles were reconstructed from that evidence. They
were not generated by SwiftPM/Xcode in the editing environment, which has
neither toolchain. Portable validation does not prove native graph resolution.
Before merging, require green macOS Build & Test and iOS E2E jobs that consume
these locks with the strict flags. Do not remove a strict flag to make a failed
resolution pass; investigate and regenerate both files with native tooling.
An iOS signed archive still needs its release validation.

## Intentional updates

On a Mac, update dependencies deliberately with `swift package update`. Review
the source revision changes, copy the resulting lock to the iOS workspace lock
path, then run `scripts/ci-ios-e2e.sh resolve` to validate it with Xcode using
strict resolution. Review and commit both lockfiles together. Run
`python3 scripts/ci-verify-dependency-locks.py`, then normal CI. Xcode may change
the lock schema or ordering; the verifier compares dependency pins, not JSON
formatting. Cache keys include both locks.

This pins the Swift dependency graph. Hosted runner images, Xcode selection,
GitHub Actions tags and Homebrew tools remain separate reproducibility and
supply-chain work. Signing credentials and binary reproducibility are not
established by a dependency lockfile.
